2.3 处理毫秒显示造成的量化误差

若平台按常规四舍五入显示两位小数毫秒，1.40 ms 对应的真实时间可能位于 [1395,1405) μs；1.39 ms 可能位于 [1385,1395) μs。把它们转成 1400.00 和 1390.00 并没有增加测量精度。

在这个显示假设下，Round 5 和 Round 6 各有两个这样的毫秒项，仅量化就使两次合计之差具有约 ±20 μs 的不确定范围；表中合计改善 12.18 μs 本身不足以证明总耗时稳定改善。小点的明显降时仍然是独立的方向性证据。

下一轮保留页面原始字符串及单位；正常授权结果页能提供更精确耗时时优先保存，不绕过权限提取隐藏数据。没有重复数据时，不能制定“低于 1% 必是噪声，高于 1% 必有效”的统一规则。配套脚本可计算显示舍入区间，但区间不是统计置信区间，不能替代重复测量。

4. 统一的成本模型与 tiling 表

4.1 逻辑流量与命令量分别计算

定义有效输出 tile 为 R 行、W 列，元素大小 e=2 字节；对于 padding 路径，以 P=align_up(W,16) 表示一个可行的 FP16/BF16 UB 行距候选，以 N=R×P 计算 UB 容量。若实现采用其他合法行距，按实际值计算。

对于整张张量，前后向的最小逻辑 GM 流量均为：

B_logical = 2 × S × D × (m + 1) 字节

题面中 (1024,4096,4) 对应 40 MiB，(8192,7168,8) 对应 1008 MiB；它们是题面示例，不是已解出的黑盒 shape。逻辑有效带宽也不等于实际 HBM 带宽，因为缓存、额外读写和计时边界可能不同。3

**推导：**若前向每 tile 一次二维读入、m 次二维写出，则 API 调用量近似 (m+1)×tile_count；若反向每 tile m 次二维读入、一次写出，则也是这个数量级。增加 R 的主要作用之一，是减少命令、地址计算、事件和循环次数，不一定减少必要字节数。

一次多块 DMA 调用也不等于硬件只进行一个完整突发传输。因此，既记录 API 次数，也记录 blockCount/blockLen，不能只看源码里 DataCopy 出现几行。

4.2 前后向独立 UB 预算

以下是候选布局的推导，不是已审阅的 Round 6 分配：

候选 活跃缓冲 约占用
前向双缓冲直接写出 两份 16-bit 输入，输出复用输入 4N 字节
反向 Cast+Add 两份 16-bit 输入、FP32 acc、FP32 temp、一份 16-bit 输出 14N 字节
反向 FP16 Axpy 两份 half 输入、FP32 acc、一份 half 输出 10N 字节

上述结果没有计入额外 padding、框架缓冲、临时区或其他并存对象；若双输出、双 accumulator 或分组预取，会进一步增长。输入为非对齐 D 时，不能用 R×W 冒充实际分配 R×P。

由此可见，同一个 8192 元素上限不必同时适用于前向、FP16 反向和 BF16 反向。 应通过平台查询取得 UB 容量与 AIV 数量，而不是写死网上某型号的核数/容量。45

4.3 任务数和流水深度需要同时满足

对每个候选 (R,W)，计算：

T = ceil(S/R) × ceil(D/W)
C = 实际 blockDim
q = floor(T/C)，r = T % C
前 r 个核执行 q+1 个任务，其余核执行 q 个任务

有效核数不能超过可用核数和任务数，但也不以“刚好铺满所有核”为唯一目标。单任务路径要分别处理一轮任务、多轮任务与尾核；双缓冲是否划算需要真实实验。官方流水文章明确指出，小数据强行双缓冲可能适得其反。6

本地生成 tiling trace，字段建议为：

S,D,m,dtype,backward,mode,R,W,P,total_tasks,blockDim,
min_tasks_per_core,max_tasks_per_core,ub_bytes,
read_calls_per_tile,write_calls_per_tile,aligned,tail_present

这些是离线分析记录，不要在提交的 device 热路径中打印。

5. 方案 A：入口、Scalar 和编译期路径轻量化

优先级 P0/P1；目标是降低小任务成本，也可能减少所有规模的每 tile Scalar 开销。

5.1 TPipe 与按需初始化

官方 API 优化文章说明，TPipe 放在 kernel 计算类内部可能使编译器对类成员别名采取保守策略；示例在 kernel 入口函数中、计算类对象外部构造 TPipe，再向计算类传指针，以利于 Scalar 常量传播。7

Agent 先检查当前代码。如果已这样实现，则明确跳过，不制造无意义重构。若未实现，只改这一项，保持算法、tile 和事件序列不变，单独验证。

接下来检查是否在选择 forward/backward 或轻量/流水路径前就初始化了所有 buffer。候选结构为“先按通用模式分派，再构造该模式需要的对象”，而不是一个巨大的 Init() 分配前后向全部状态。

5.2 通用微内核分类

候选分类如下，名字仅供工程组织参考，不要求创建新的提交文件：

FWD_ONE_TILE
FWD_PIPELINED
BWD_FP16_CAST_ADD          # 保留稳定回退
BWD_FP16_AXPY              # 验证后启用
BWD_BF16_FP32_ACCUM
GENERIC_TAIL_OR_FALLBACK

编译期只固化高价值的方向/dtype/模式，随后再考虑 m=2/4/8 的短循环展开；S、D 仍从 tiling 取得。不把所有 R×W×m×dtype×mode 做笛卡尔积，避免编译产物和指令体积失控。模板配置必须沿用本机 8.5 可编译的接口，Host key 编码、kernel 模板顺序和产物一一对应。8

5.3 热循环算术外提

审查 task / num_d_tiles、task % num_d_tiles、s*m*D、blockLen/stride 计算是否反复发生。可把合法的 shape 推导和循环常量移到 Host tiling，或每核计算一次后用指针递增；Host 仍不做输入数值计算。

不要为了省 64-bit 指令而全盘把地址乘法降成 32-bit：S×D×m×2 和偏移要先做溢出检查。DMA 参数本身的小整数位宽，也不能充当完整 GM 地址位宽。

**验证信号：**分派与结果不变；轻量路径初始化更少；能获得汇编/模拟热点时，Scalar 负担下降；线上变化超过重复噪声后才合并。点号只用于观察，不用于代码判断。

6. 方案 B：FP16 反向的混合精度基础 Axpy

优先级 P1；这是本轮最值得独立验证的新计算候选之一。

6.1 为什么它不同于 Round 4 的 half Add

8.5 路径的基础 Axpy 文档列出 half 源、half 标量、float 目标的组合，并给出该组合的示例。基础 Axpy 与带 sharedTmpBuffer 的高阶同名 API 不是同一成本模型；本方案研究基础接口。910

待验证的算法是：先把第 0 路转为 FP32 accumulator，后续以系数 1 做 acc += input_half，最后仅一次转换回输出类型。acc 始终是 float，不是每一步都舍入回 half。

局部调用示意如下；只展示计算替换，未包含分配、流水同步、padding 与最后写回，不是可直接提交的完整 kernel：

// acc: LocalTensor<float>
// x0 / xk: LocalTensor<half>
// count: 本次合法计算的元素数；各 buffer 已完成必要的跨流水同步。
AscendC::Cast(acc, x0, AscendC::RoundMode::CAST_NONE, count);
// 对后续 k 按基线顺序执行：
AscendC::Axpy(acc, xk, static_cast<half>(1.0), count);

6.2 本题上的推导收益与失败条件

在一个源需要“Cast 到 temp，再 Add 到 acc”的实现中，这个候选有机会去掉后续流显式 temp 写入/读出和一部分向量调用，并减少 FP32 临时缓冲。真实编译结果可能存在展开、额外控制或不同吞吐，不能按“源码少一行”估计速度。

对 m=8，源级常见路径是 8 次升精度 Cast、7 次 Add、1 次降精度 Cast；候选是 1 次升精度 Cast、7 次 Axpy、1 次降精度 Cast。这只是调用量对比，不是硬件指令数量或预计加速比。

第一版仅替换计算，保留 Round 6 的 R/W、任务分配、m 顺序与同步边界。第二个独立实验才利用省下的 UB 扩 tile；否则无法辨认收益是 Axpy 还是 tiling 带来的。

6.3 必须执行的防护

BF16 在该基础 API 的已列类型组合中没有对应混合路径，继续使用 BF16→FP32 Cast+Add，不能转换成 half 来硬套。高维 Axpy 混合模式的 PAR 为 64；若改用 repeat 接口，源/目标 stride 必须按各自字节宽度推导，不能直接照抄 half/half 的参数。9

保留基线最终 Cast 模式。Cast 文档对 dtype、舍入、地址重叠和位宽变化有单独限制；同一地址原地从 16-bit 扩成 32-bit 尤其不能想当然使用。11

验证 finite 极值、正负抵消、大小值混合、subnormal（若题目契约覆盖）、不同 m、非对齐尾块。即使数学上乘 1 不改变输入，也要确认硬件舍入/溢出与参考契约一致。

**停止条件：**头文件不支持、实际指令未减少、精度不符或平台反向收益不能复现，就保留原 Cast+Add。不得为了开启该路径放宽误差阈值、改变参考、缩小合法域或删除 BF16 支持。

7. 方案 C：前后向独立容量与大规模任务组织

优先级 P1；优先研究通用“大工作量且任务充分”域，不改小任务已有效策略。

7.1 前向不要继承反向临时缓冲的容量限制

记录中的 8192 上限使 D=7168 时每 tile 只合并一行。作为本地例子，若前向仅两个 16-bit 输入 buffer：

R=1, W=7168：N=7168，双输入约 28 KiB
R=2, W=7168：N=14336，双输入约 56 KiB
R=4, W=7168：N=28672，双输入约 112 KiB

这是容量推导，不保证平台具有足够可用 UB，也不保证更大 R 更快。它说明“一行已触到 8192 元素上限”不等于“已触到前向真实 UB 上限”。1

可先在本地候选集中比较前向 N_max=8192/16384/32768，按平台容量、总任务数、合法 stride 和每核循环数过滤。参数是搜索起点，最终用可解释的容量/规模条件决定分派，绝不能为 (8192,7168,8) 写专用白名单。

7.2 反向分别考虑 Cast+Add 与 Axpy 预算

保守起点可比较 N_max=4096/8192/12288；更大的候选必须通过真实 UB 分配核算。FP16 Axpy 与 BF16 Cast+Add 可拥有不同容量上限。一次只修改一个方向/计算模式，不使用一个全局 tile 常数同时改变所有路径。

7.3 连续分配与跨步分配做单独消融

若现在每核 task += blockDim，可比较每核一段连续 task 区间：

q = T / C
r = T % C
count(c) = q + (c < r)
start(c) = c*q + min(c,r)

这是覆盖所有任务且每任务唯一归属的算术分配。它可能改善局部地址推进，也可能使多个核同时访问的地址分布更差；不预设优胜。保持 tile 与计算不变，单独比较。

7.4 Round 5/6 中点 2、4 的回退需要查边界

Round 5→6 的点 2 为 16.24→16.62 μs，点 4 为 47.88→50.60 μs。先比较公开代表 shape 在两个版本的 tiling trace 与选中路径。若中等任务不应变化却变化了，应缩小“小任务并行度保护”影响范围，而不是全局回滚。没有原始代码和重测时，不能认定回退已经被某项参数确定解释。1

8. 方案 D：反向沿 m 分组读取，但保持每个输出的加法顺序

优先级 P2；在源码/模拟热点显示读命令或 Scalar 调度较重时尝试。它与增大 R 是不同维度的实验。

8.1 W=D 时的连续流分组

反向输入是 [S,m,D]。同一 token 的相邻流在 GM 中连续；当前按某个 k 一次取多行，是利用 S 维的二维 DMA，而不是利用同一 token 内 m 路的连续性。可尝试每次读入 G 个相邻流，局部布局为 [R,G,D]，再按原始 k 顺序累加。G 可从 2、4 或 m 开始搜索，并处理最后不足 G 的组。

在 W=D 时，每个 token 的 G 路可以合成一个连续块；以字节为单位，其块长为 2×G×D，相邻 token 块之间的 GM 间隔为 2×(m-G)×D。一次多块调用可覆盖 R 行。真正传给 API 时，必须按该重载转换长度/间隔单位并检查范围。1213

若 W<D，不要继续使用上述“大块连续”的公式。取完整 m 路时，可以推导为 R×m 个宽 W 的块、块间 GM 间隔 2×(D-W)；若只取 G<m 路，跨 token 的间隔与同 token 内的间隔不同，通常不能由一个相同步长的简单二维调用表达，应分层循环或回退。

8.2 UB 成本不能遗漏 G 倍输入

若有两份 16-bit 分组输入，容量就是 4×G×N 字节，不再是 4N。加上一份 FP32 acc、一份流级 FP32 temp 和一份 16-bit 输出，总量约为：

Cast+Add 分组输入方案：U ≈ (4G+10)N 字节
Axpy 分组输入方案：   U ≈ (4G+ 6)N 字节

这些公式假设 FP32 temp 每次只容纳一流；若把整个 G 流组一起 Cast，临时区也会按 G 增长，必须重新计算。局部行距 padding 和其他同时活跃缓冲仍需另加。

因此，不建议直接“把所有 m 路全部装进 UB”。它可能减少读调用，却造成 tile 缩小、Vector 处理碎片化、等待增多，最终更慢。仅在不同 G 的 DMA 调用数、向量调用数和真实耗时都留档后决定。

8.3 不靠改变归约树获得未经确认的速度

不同 D 切片之间可以交错调度，各切片内部仍按 k=0,1,… 累加。这样有机会利用独立输出的并行性，而不主动改变每个输出的求和顺序。相反，把 m 路改为平衡树、多个部分和最后再合并，会改变 FP32 舍入次序；必须作为独立精度实验，不纳入第一版。

9. 方案 E：同步、mask 与 BF16 路径的后续优化

9.1 先画 buffer 生命周期，再减少事件

前向 raw UB 路径至少有两条关键依赖：MTE2 写完后 MTE3 才能读；同一 buffer 最后一个副本写出不再读取该 UB 后，下一次 MTE2 才能覆盖它。不能在第一个副本发出后就释放给下一轮输入。

反向至少包含：输入 DMA 完成→Vector 读取；输入最后一次 Vector 读取完成→输入 buffer 复用；最终 Cast 完成→MTE3 写出；MTE3 读完输出 UB→下一轮 Vector 覆盖输出。Cast 和 Add 都使用 Vector 路径，不能仅因它们是两个 API 就声称能像 MTE2/Vector 那样独立同时执行。

对每个 buffer 写出如下表，所有事件都必须能对应到依赖：

对象 写入者 最后读取者 何时可覆盖 当前保护机制
前向输入 p MTE2 第 m-1 路 MTE3 最后一次读完成 从源码填写
反向输入 p MTE2 Cast/Axpy 对该输入最后一次 Vector 读取完成 从源码填写
反向 acc Vector 最终 Cast 本 tile 计算完成且消费者已读 从源码填写
反向输出 p Vector MTE3 写出不再读取输出 UB 从源码填写

SetFlag/WaitFlag 的事件类型、ID 分配及复用按 8.5 实际接口处理，不用“删掉所有 Barrier 再试”的方式优化，也不硬编码可能与队列冲突的事件 ID。特别测试只有 1/2/3 个 tile 的序言/稳态/尾声路径。14

9.2 Counter mask 与 m 短循环

BF16 路径先保持 Cast→FP32 Add→最终 Cast。若热点表明 Scalar 参数设置明显，再比较外部 mask、固定 m 的循环展开、减少重复参数生成。SetVectorMask 文档区分普通与 Counter 模式；外部 mask 必须配套正确的 isSetMask=false 接口，完成后恢复模式/掩码，不能把一个 16-bit 向量参数直接套给 16→32-bit Cast。1511

先检查 count 重载实际生成的代码：编译器或 API 实现可能已经做了类似优化。若生成代码未变，就不应把改写 API 样式当成性能改善。

9.3 前向 UB 展开暂列 P3

构造 [R,m,W] UB 输出后连续写出，可能以本地复制和更大的 UB 占用换取较少的 GM 写命令。它并非无条件优于当前“同一输入复用 m 次写出”。只有在 MTE3 发射间隙或写出碎片明显时才加入对比，不重新引入没有测量理由的 UB→UB 复制。

普通 DMA 的零源间隔通常是“源块首尾相接”，不是“对同一源块反复广播”。相关广播/Tile 样例只能用于布局学习，不能靠把 stride 设 0 实现重复源。1213

10. DMA 与尾块正确性核查清单

先在笔记中用统一的字节偏移推导，再转换成具体 API 参数，避免在一张表里混用单位。

操作 GM 起点（元素） 连续有效宽度 相邻 GM 块之间间隔（字节）
前向读输入 R 行 s*D+d W 2*(D-W)
前向写某个 k 的 R 行 (s*m+k)*D+d W 2*(m*D-W)
反向读某个 k 的 R 行 (s*m+k)*D+d W 2*(m*D-W)
反向写输出 R 行 s*D+d W 2*(D-W)

这里是块与块的间隔，不是块起点之间的总距离。最后一块是否需要间隔、末行/末列的有效长度，由实际 DMA 调用定义处理。

普通 DataCopy 的相应多块接口以 32 字节 datablock 表达块长和间隔，而 DataCopyPad 的 DataCopyExtParams 块长按字节、GM 一侧间隔按字节、UB 一侧间隔按 datablock。不同重载的字段、类型和上限以本机头文件与文档为准。普通 count 形式不能用于未满足所需对齐的完整尾长；不能以截断搬运蒙混过去。1213

需要单独验证：

  • R 尾行与 W 尾列同时出现；m 分组最后不足 G；D=1 和极小 S。
  • UB 行首满足 API 对齐；padding 区若进入实际 Cast/Add，需合法初始化或用正确掩码排除，不能只以“不影响有效输出”为由读未初始化数据。
  • 所有 blockCount/blockLen/stride/repeat 参数可表示；太大时继续分块，不能静默窄化整数。
  • 每个有效输出元素恰好写入一次；无跨核覆盖，无漏写；输入读取与输出写出均不越界。
  • 通用 fallback 对所有声明的合法输入真实执行并写出，不是 return、错误码或 host 代算。316

11. 无 NPU 时新增的实际分析路线：.o + JSON

11.1 不必把“先写完整 runner”当成唯一前提

8.5 的 msProf 文档支持用 kernel .o 和 JSON 配置进行算子调测，模拟器也接受 --config 路径。这给目前没有完整 runner 的工程增加了一条尝试路线。它并不免除导出真实 tiling、匹配入口 ABI、准备输入和比对输出的工作。1718

建议先做一个小型 FP16 forward 合法形状，再做 FP16 backward，再验证 BF16 工具输入支持与对应产物。只在同一个已验证配置上更换实验 .o，避免把工具配置错误当作 kernel 退化。

11.2 Agent 需要从真实工程导出的内容

配置 取得方式

12. 正确性与回归测试矩阵

12.1 不是重测 reference，而是测试实际新 kernel

保留已有 reference 测试，但把每项候选的“数值验证通过”限定为实际 kernel 输出与 golden 的完整比较。暂时没有可运行环境的候选，只能写“已编译、待执行”，不能升级成精度通过。

选择成对覆盖，不生成所有维度的笛卡尔积。测试集合包括：S 取 1、2、3 及 R/任务划分边界附近；D 取 1、15/16/17、255/256/257、8191/8192/8193 以及实际 W±1；m 取 1、2、3、4、5、7、8、9。另加题面三类典型规模和固定随机种子的小规模随机组合。用未参与调参的独立随机集合做 holdout。3

这些值是自构造测试建议，不表示线上存在这些点。巨型测试先估算输入+输出+golden 总占用，避免主机内存溢出掩盖真正问题。

12.2 数据分布与精度顺序

常规随机之外，至少包括常数、全零、正负交替、可表示大值相消、大小值混合。保留原始最终 Cast 模式；超出题面明确数据范围的 NaN/Inf、subnormal、最终结果溢出等，单独标注为扩展契约测试，不在不知情时修改 golden 容忍度。11

两个有针对性的推导例子：

FP16 输入 [40000,40000,-40000,-40000]
数学和为 0；逐次 half 累加可能中途溢出，FP32 累加可避免这一中间溢出。

BF16 可表示输入 [2^26,1,-2^26,1]
以普通 round-to-nearest FP32 顺序累加可得到 1；
按 (a+b)+(c+d) 组合可得到 0。

第二个例子说明“都用 FP32”也不等于“可以任意改变归约树”。这里是浮点运算推导，不是线上输入范围的断言。Axpy、分组预取和 m 展开优先保持基线 k 顺序。

12.3 定义正确性闸门

每个候选分别记录：8.5 binary/install、两个 dtype 对应产物、实际 kernel 执行状态、完整输出对比、尾块/边界测试、线上 8/8 状态。没有真实执行条件的本地项写未完成；线上通过记录只覆盖平台实际测试域。

13.2 预算与测量

上传赛事说明写有每日最多 5 次提交。可以把一个批次分配为：1 次稳定对照、最多 3 个已通过本地闸门的独立候选、1 次优胜候选复测。未完成验证就少提交，不凑满次数；后续批次再推进剩余实验。2

有真机时，固定输入生成与计时边界，交错执行基线/候选，保留 warm-up 与多次重复结果、median、MAD 和范围。不要以大量重复中的单次最小值作为唯一收益。线上若只有一次结果，就明说“单次观测”，不造置信度。

13.3 合入标准

正确性与规则是前提。一个候选只有在代码 diff 可解释、数据支持收益、关键旧路径无不可接受退化时才进入下一父版本。总耗时与平台真实分数同时观察；页面最优不是硬性速度上限。

当小点改善而某个大点退化时，先按实际计分规则衡量，不以“改善了更多点”投票。若差异被显示量化覆盖，标记待复测而不是宣布胜利。

若合并后性能变差，按机制开关逐项回退。相同机制重复尝试没有新证据时暂停，把精力移到有源码/模拟信号支持的方向。

14. 合规、版本与不做事项

所有分派依赖可解释的 dtype、方向、容量、对齐、任务数和 m 属性，不写八个点的索引或具体 shape 白名单。分支覆盖的声明域需要任意合法输入正确，generic fallback 必须真实计算并写 GM 输出。16

题面要求前向复制，而 R6 禁止纯搬运，这一文本边界仍需要赛方书面澄清；当前平台 Pass 不能替代最终代码审查。本方案中的前向 DMA 优化是技术候选，不作合规豁免判断，也不能靠加零/乘一等无用算术掩饰。

不优先做：跨核 AtomicAdd 归约、先转置整张大张量、将题目改成 Cube Matmul、回退到 Host 计算、输出 view/alias 替代独立写出、结果缓存重放、整个 m 维无预算地全驻留、以及把 Round 4 多项改动原样打包重试。

官方 asc-devkit 变更记录区分 8.5.0 与 9.x；查源码优先使用与 CANN 8.5.0 对应版本、本机头文件和编译产物。最新主线的 BF16 支持、新宏或 API 不能直接推定适用于本题。21
